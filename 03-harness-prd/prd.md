## Problem & user

Help a Webex Calling product manager identify recurring product issues, ideas, and requests related to Control Hub Administration and the Provisioning Layer. Bring relevant feedback together, preserve source evidence, prioritize signals that need attention, and show whether an existing Jira backlog item may already cover the work.  The existing prototype provides the interaction pattern: ranked signal cards, category filters, search, evidence details, and local demo mapping to existing Jira items. This extension adds source filters and source coverage for Airtable and Community.Cisco. All prototype feeds, counts, messages, and Jira items remain synthetic until separately authorized integrations are configured.. Juno does this inside limits a human set on purpose, and defends every call it makes.

## 01 Context · Data Requirements

**Required sources, and exclusions**

Webex Spaces: User-selected spaces relevant to Calling Provisioning / Control Hub Administration
Airtable Features: Feature-request records assigned to the authenticated/current user
Community.Cisco: [Webex & Collaboration track](https://community.cisco.com/t5/webex-and-collaboration-track/ct-p/2331j-collab-ccp)
JIRA: This is where the backlog actually lives and should be compared for existing tickets when referencing the signal data.

**How fresh must it be**

Should always be pulling latest from context depending on the frequency defined. These sources are primarily async communication vectors where clarifications will come in periodically. When a source is unreachable, flag that and move on with the other sources. Do not REMOVE any data from the tool because a source is unreachable. Simply mention that a given source (e.g. Airtable) is experiencing connection issues for the moment which may require human input to resolve.

## 02 Tools · System Capabilities

**The verb list**

Webex Spaces: Retrieve selected space metadata and message history; retain source/thread/date references
Airtable: Read matching records and permitted fields; show source record link and last-read time
Community.Cisco: Read accessible posts, replies, dates, titles, and URLs needed to identify feedback
JIRA: Read and search for tickets which correspond to signals. 

**Deliberate omissions**

No write permissions are granted across any of the context vectors.

## 03 Loop · AI Costs & Latency

**Turn ceiling and escalation**

One pass per batch of signals.

**Latency and cost target**

This is not intended to be a real-time tool run constantly. It will be scheduled with an option to run ad-hoc if required but a slight process time is acceptable

## 04 Memory · Data Requirements

**What persists, at what scope**

Memory should include the previous output as a baseline and pull for new insights based upon when the previous concluded. We should retain source content and signal summaries for the previous run to compare against as a means of consistent output matching (monitor own tool accuracy).

**Expiry and write rules**

Keep a previous run one time for comparison against current run. After that, current run is source of truth. When a human gets involved to correct, the human speaks with authority. Persist human feedback over what has been mined from the sources when conflict.

## 05 Permissions · AI Risks & Mitigations

**The permission tier**

| Side-effect class | Tier |
|---|---|
| read | auto |
| draft | blocked |
| write | blocked |
| send | blocked |

**Justification**

It can perform READ-ONLY actions against the context provided. The tool is to never write/edit/delete anything within the context sources. It then can update the signals dashboard based upon the information.

## 06 Verification · AI Testing & Measurement

**The check before output ships**
- Report which sources were read, their scope, the history window, and the last successful read time.
- Mark unavailable or partially read sources clearly. Never imply that an unavailable source was scanned.
- Link every signal to its supporting source records or conversations. Summaries and cross-source groupings that go beyond the source text must be identified as AI-generated interpretations.
- Show the evidence behind frequency, recency, trend, and confidence indicators. Count distinct conversations or records, not individual replies or repeated copies of the same request.
- Treat Jira matches as suggestions for PM review. Show the issue key, title, status, and when those fields were last read; do not create or change Jira issues.
- Treat human corrections as attributed review decisions. Preserve the original evidence and record what the PM changed.
Evaluation set

Maintain a versioned set of representative, synthetic or approved examples with expected source coverage, product relevance, evidence links, signal grouping, duplicate handling, and Jira match. Include:
- A recurring request across multiple Webex conversations.
- A request appearing in more than one source that may refer to the same underlying report.
- A stale, resolved, or superseded request.
- A Community post with replies, where replies support the thread but do not each count as a separate request.
- Content outside the Webex Calling / Control Hub scope.
- An unavailable source, sign-in failure, or partial scan.
- A signal with no suitable Jira match and one with a plausible existing match.
Initial release gates — proposed for PM calibration
- 100% of displayed signals have traceable supporting evidence.
- 0 fabricated source records, Jira issues, or claims that an unavailable source was scanned.
- 100% of runs disclose source scope, scan window, and per-source success or failure.
- At least 90% precision on the reviewed set for product relevance and signal grouping.
- At least 80% PM agreement that the top-ranked signals deserve attention, with ranking explanations visible for every signal.
- Jira suggestions are reviewed separately; measure false matches and missed existing coverage before enabling live linking.
Treat these percentages as starting targets to validate with PMs, not as established performance.

Pilot measures

For each pilot, track evidence traceability, relevance and grouping agreement, duplicate handling, Jira match accuracy, PM corrections, source coverage and freshness, and time to review a signal. Review errors by source and category before expanding access or scope.

**Failure behaviour**

Helpful but cautious when running into an issue. Always be abundantly clear when dealing with ambiguity. Do NOT assume, hypothesize, or make up anything.
